# 免费代理软件

> 直接结论：客户端可以免费获得，它连接的服务器不行。判断一款代理软件是否值得装，先看发布来源与安装包能否核验，再看它拿到什么系统权限，最后比较协议与界面。Mihomo、Xray-core、sing-box 属于内核，Clash Verge Rev、Mihomo Party、v2rayN、v2rayNG 属于外壳，版本错配时先查版本与日志，换节点解决不了。

## 结论与适用边界

先给三条可以立刻执行的判断。

第一条，来源决定风险上限。同一个客户端，从项目官方仓库的 Release 下载，与从聚合下载站下载，代码可能完全不同。前者可以用校验和与签名验证，后者只能靠对方的信誉，而信誉无法复算。

第二条，权限决定能力边界。系统代理只影响愿意读取系统代理设置的应用，TUN 接管路由层，需要管理员或系统扩展授权。Android 走 VpnService，iOS 走 Network Extension。授权范围不清楚时，先别点确认。

第三条，分工决定排查顺序。图形界面、内核、配置、订阅、线路是五层，故障时按层排除。界面显示已连接但本地端口没有监听，问题在进程层，改规则和换节点都不会有结果。

### 适用边界

- 只讨论可公开核验的开源项目与官方文档，包括 Mihomo、Xray-core、sing-box、v2rayN、v2rayNG、FlClash、Hiddify、Clash Verge Rev、Mihomo Party、OpenClash、ShellCrash 等。
- 不评价具体商业客户端的性价比，也不给出 iOS 应用的购买建议。商店地区与 TestFlight 只解释分发机制。
- 不承诺版本号、下载量、协议兼容性与节点可用性。版本信息以官方发布页和项目文档为准。
- 不提供规避执法、规避实名制或绕过企业网络管理的操作步骤。
- 不同司法辖区对代理工具的规定不同，使用前自行确认当地法律、服务条款与可接受使用政策。

### 判断依据

本页的技术判断来自四类材料，RFC 规范、内核项目的官方文档、平台开发者文档、官方仓库的发布页。四类之外的材料只作为线索，不作为结论。正文出现的数值都标注单位与条件，没有条件的数值不写。涉及价格的段落一律标注测算假设，不冒充市场报价。

## 这个专题解决什么问题

搜索“免费代理软件”的人通常带着一个具体故障，而故障发生在哪一层，决定该读哪一节。把问题按层分开，能省掉大量重复安装和反复换节点的动作。

### 四类具体问题

来源问题。搜索结果前排经常是聚合下载站，安装包被重新打包，附带启动器、主页锁定、额外的后台服务。这类包不一定有恶意代码，但它已经脱离了项目方可验证的范围，出问题时无法用哈希和签名回溯。

选型问题。同一台电脑装了两个客户端，都默认监听同一个本地端口，第二个启动就报端口占用。另一种情况是客户端不支持订阅里的协议，节点能显示出来，连接一直失败，日志里出现无法识别的字段。

权限问题。不理解系统代理与 TUN 的差别，开了系统代理却发现某个应用完全不走代理；或者为了开 TUN 长期保留管理员权限，把内核漏洞的影响面从当前用户扩大到整台机器。

维护问题。升级后配置字段不兼容，订阅解析失败，内核与 GUI 版本错配。日志里出现字段错误或协议不支持，用户却按“节点失效”处理，越换越乱。

### 谁该读

第一次在 Windows、Android、macOS 上安装客户端的人，读完能知道每一个下载与授权动作对应什么后果。从第三方站下载过安装包、想确认有没有问题的人，可以按核验一节逐项检查。订阅导入失败、TUN 模式无网络、端口冲突的人，可以直接看故障现象与层级的对应表。在 OpenWrt 或 Linux 网关上部署透明代理的人，重点看路由、DNS 与防火墙三节。需要判断某个客户端是否仍在维护的人，看发布页与维护状态的判断方法。

### 谁不必读

已有稳定服务、只比较价格的人，直接看便宜梯子与机场推荐两个专题。想找“最好用客户端排名”的人，这里没有排名，也不打算做。需要在 iOS 上完成购买决策的人，本页只解释商店地区与测试分发的机制。企业网络管理员也不适合读，本页不讨论绕过管理策略的方法。

### 本页不回答什么

不回答哪个机场快、哪个节点能解锁某个流媒体服务。不回答如何让代理流量不被检测。不回答具体版本的兼容性承诺，因为版本会变，承诺会过期。不回答账号地区切换的具体操作。这四类问题要么依赖未公开的实时数据，要么涉及绕过他人管理策略，都不在本站的写作范围内。

如果你只想知道先装哪个，跳到决策树一节。如果你已经装好但连不上，跳到故障现象与层级对应表。如果你还在判断“免费软件是否安全”，先读安全边界一节，再回来看安装步骤。

## 概念与实体关系

这个专题里有十个反复出现的实体。把它们的依赖关系画清楚，故障定位就有了固定顺序，不必靠猜。

### 十个实体

| 实体 | 作用 | 常见形态 | 出问题时先看哪里 |
| --- | --- | --- | --- |
| 协议规范 | 定义握手、认证与加密方式 | Shadowsocks、VMess、VLESS、Trojan、Hysteria2、TUIC、WireGuard | 服务端与客户端参数是否一致 |
| 内核 | 解析配置、建立隧道、提供本地端口 | Mihomo、Xray-core、sing-box | 内核日志与退出码 |
| 图形客户端 | 编辑配置、启停内核、写系统代理 | Clash Verge Rev、Mihomo Party、v2rayN、v2rayNG、FlClash、Hiddify | 界面报错与版本号 |
| 订阅 | 服务端下发的节点清单 | Base64 链接、Clash YAML、sing-box JSON | HTTP 状态码与解析日志 |
| 配置文件 | 内核实际读取的最终文件 | YAML 或 JSON | 配置校验命令的输出 |
| 规则集 | 决定直连、代理、拒绝 | 内联规则、远程 rule-set | 连接日志里的命中规则 |
| 系统代理 | 告诉应用把请求发给本地端口 | WinINET 设置、macOS 网络服务、环境变量 | 应用是否遵循系统设置 |
| TUN 虚拟网卡 | 在路由层接管流量 | wintun、utun、/dev/net/tun、VpnService | 路由表与提权状态 |
| 发布页与校验文件 | 提供安装包与完整性证据 | GitHub Release、checksums、detached signature | 哈希与签名结果 |
| 权限 | 决定上述组件可用范围 | 管理员、系统扩展、VPN 授权 | 系统设置里的授权记录 |

### 实体关系

| 主体 | 关系 | 客体 | 机制 | 断裂后的表现 |
| --- | --- | --- | --- | --- |
| 图形客户端 | 启动并调用 | 内核 | 生成配置后以子进程或系统服务方式运行内核 | 界面显示已连接，本地端口无监听 |
| 订阅 | 解析生成 | 配置文件 | 客户端把订阅内容转换成内核格式 | 节点列表为空或字段缺失 |
| 内核 | 监听 | 本地代理端口 | 常见默认值为 7890 或 10808 与 10809 | 启动日志报端口被占用 |
| 系统代理 | 指向 | 本地代理端口 | 写入系统设置或环境变量 | 不读取该设置的应用直接绕过 |
| TUN | 改写 | 路由表 | 把默认路由指向虚拟网卡 | 权限不足时无法创建网卡 |
| 规则集 | 被引用 | rules 列表 | 首条命中的规则生效 | 顺序错误会让后续规则失效 |
| 发布页 | 提供 | 安装包与校验和 | 哈希与代码签名 | 哈希不符或签名主体不对 |
| 权限 | 授权 | TUN 或系统代理 | 系统弹窗、管理员确认、服务安装 | 拒绝后功能降级或无法启动 |

### 一张关系图

```text
[官方发布页 Release]
      │ 下载安装包 + 校验和 + 签名
      ▼
[图形客户端 GUI] ──── 生成 ────► [配置文件 YAML / JSON]
      │                                  │ 读取并校验
      │ 写系统代理                        ▼
      ▼                            [内核 core]
[系统代理设置]                            │
      │ 部分应用遵循                      │ 监听 127.0.0.1:port
      ▼                                   ▼
[应用请求] ───────────────────────► [本地代理端口]
                                          │ 隧道握手
                                          ▼
                                   [远端出口] ──► [目标站点]

[TUN 虚拟网卡] ──── 默认路由 ────► [内核转发]
```

图中有一条容易忽略的边，图形客户端并不转发流量。它只负责生成配置、启动内核、把系统代理指向内核。流量路径里没有 GUI，所以 GUI 卡死时连接可能仍然正常，GUI 正常时连接也可能完全不通。

### 三条依赖链

安装链从发布页开始。发布页给出安装包、校验和、可选的签名文件。任一环节缺失，后面的动作都失去验证基础。这条链断裂的典型表现是安装包能装、程序能开，但版本号与官方发布页对不上。

配置链从订阅开始。订阅被解析成配置文件，内核读取前会做一次校验，校验失败的字段会被忽略或导致启动失败。这条链断裂时，界面通常还能显示节点，因为节点列表来自订阅文本，不来自内核。

数据链从应用开始，经过系统代理或 TUN，进入本地端口，再经隧道到出口。这条链断裂的表现最直接，网页打不开、握手超时、只有部分应用异常。排查时先确认数据链走到哪一跳断了，再回头查前两条链。

### 三个常被混淆的区分

订阅不是协议。订阅是一份文本，里面可以同时包含多种协议的节点。客户端支持订阅格式，不代表支持里面所有协议。导入成功、连接失败，多数时候问题在协议支持，订阅本身没有坏。

内核不是服务。内核只提供本地端口和隧道能力，它不提供任何服务器。把内核装好、配置写成空文件，客户端仍然无法上网。软件免费与服务免费是两件事，这一点在成本一节会用量化方式展开。

GUI 不是内核。同一份配置可以喂给不同 GUI，同一个 GUI 也可以切换多个内核。遇到“同一个订阅在别的客户端能用”这类现象，先比较两边的内核与配置字段，再比较界面设置。

### 组件之间的版本约束

GUI 对内核有版本要求，通常写在发布说明或配置文件里。内核新增字段后，旧 GUI 可能无法识别；内核移除字段后，新 GUI 生成的配置在旧内核上会报错。订阅内容也会随服务端升级而变化，服务端启用新传输方式时，旧内核可能直接拒绝连接。三个版本变量同时存在，排查时必须分别记录，不能只写“客户端已经更新过”。

## 技术参数与平台矩阵

这一节只放能标注单位、口径与数据性质的参数。没有条件的数字不进入表格，例如“平均速度快”“延迟低”这类描述，无法复核，也不构成技术参数。

### 参数对比表

表中“数据性质”分四类。规范值是协议或标准规定的固定值。计算值由公式推导得出。平台机制由操作系统或运行时决定。工程惯例是长期形成的默认做法，可以被修改。

| 参数 | 取值 | 单位 | 口径与条件 | 数据性质 | 对判断的影响 |
| --- | --- | --- | --- | --- | --- |
| TCP 建连往返 | 1 | RTT | 完整三次握手，不含 TLS | 规范值，RFC 9293 | 首包延迟的下限 |
| TLS 1.3 完整握手 | 1 | RTT | 无会话恢复，首次连接 | 规范值，RFC 8446 | 首次访问比恢复多一个往返 |
| TLS 1.3 会话恢复 | 0 至 1 | RTT | 0-RTT 存在重放风险，需应用配合 | 规范值 | 影响二次打开速度 |
| QUIC 握手 | 1 | RTT | 首次连接，已含 TLS 1.3 | 规范值，RFC 9000 与 9001 | UDP 可用时降低建连延迟 |
| 以太网 MTU | 1500 | 字节 | 标准以太网帧的负载上限 | 工程惯例 | 超过即分片或丢弃 |
| PPPoE 环境 MTU | 1492 | 字节 | 拨号封装占用 8 字节 | 计算值 | 部分家宽需要下调 |
| IPv6 最小 MTU | 1280 | 字节 | 链路必须支持，中途不得分片 | 规范值，RFC 8200 | IPv6 下调整空间更小 |
| WireGuard 单包开销 | 约 60 | 字节 | IPv4 20 加 UDP 8 加协议头 32 | 计算值 | 有效载荷约 1440 字节 |
| TCP MSS（IPv4） | 1460 | 字节 | 1500 减 20 减 20 | 计算值 | 隧道内需要 clamp |
| DNS 默认端口 | 53 | 端口 | UDP 为主，响应截断后转 TCP | 规范值，RFC 1035 | 容易被本地解析器绕过 |
| DoH 与 DoT 端口 | 443 与 853 | 端口 | HTTPS 与 TLS 承载 | 规范值 | 可能与代理端口冲突 |
| 本机代理端口 | 7890 或 10808 与 10809 | 端口 | 客户端默认值，可修改 | 工程惯例 | 两个客户端同时启动会冲突 |

| Android 活动隧道数 | 1 | 条 | 系统限制，同时只能有一个 VPN 应用 | 平台机制 | 两个客户端不能同时工作 |
| Windows 系统代理作用域 | 当前用户 | 注册表键 | HKCU 下的 Internet Settings | 平台机制 | 切换用户后设置不跟随 |

表中 WireGuard 的开销按 IPv4 计算。IPv6 下头部从 20 字节变成 40 字节，总开销约 80 字节，有效载荷相应减少。这类差异在隧道叠加时会被放大，因为每一层封装都要占掉一部分 MTU。

### 平台矩阵

| 平台 | 安装来源 | 权限模型 | 流量接管 | DNS 处理 | 主要限制 |
| --- | --- | --- | --- | --- | --- |
| Windows | 官方 Release，部分项目有包管理器清单 | 普通用户可写系统代理，TUN 需管理员或系统服务 | 系统代理或 wintun 虚拟网卡 | 系统解析器或内核 DNS | UWP 应用回环限制，双客户端抢端口 |
| Android | 官方 Release 的 APK，少数项目在应用商店 | 建立隧道需 VpnService 逐次授权 | 仅 VpnService | 内核 DNS 或系统解析器 | 同时只能有一个 VPN 应用，后台省电策略 |
| iOS | App Store 按账号地区可见，或 TestFlight | Network Extension 授权 | 系统级隧道，由配置决定范围 | 由客户端配置接管 | 商店地区限制，测试版有效期，无法侧载 |
| macOS | 官方 Release 或 Homebrew cask | 系统代理免提权，TUN 需 helper 或系统扩展 | 系统代理或 utun 虚拟网卡 | 系统解析器或内核 DNS | 公证与 Gatekeeper，网络服务绑定 |
| OpenWrt | opkg 软件包或项目提供的安装脚本 | root | TPROXY、REDIRECT 或 TUN | dnsmasq 劫持与转发 | 闪存空间有限，固件升级丢配置 |
| Linux | 发行版包管理器或官方二进制 | root，或仅授予 CAP_NET_ADMIN | 环境变量、系统代理、TUN、TPROXY | systemd-resolved 或 dnsmasq | 无桌面环境需手写配置，策略路由较复杂 |

这张表解释了一个常见困惑，为什么同一个订阅在手机上能用、在电脑上不能用。差异通常不在订阅，而在权限模型与接管方式。手机端强制走 VpnService，所有流量默认进入隧道；桌面端如果只开了系统代理，不读取系统代理的应用就完全绕过。

### 协议支持

| 协议 | 设计定位 | 传输与加密 | Mihomo | Xray-core | sing-box |
| --- | --- | --- | --- | --- | --- |
| Shadowsocks | 轻量加密代理 | TCP 与 UDP，AEAD 加密 | 支持 | 支持 | 支持 |
| VMess | 带身份校验的代理协议 | TCP 为主，可套 TLS 或 WebSocket | 支持 | 支持 | 支持 |
| VLESS | 无内置加密，依赖外层 TLS | TCP 与多种传输 | 支持 | 支持 | 支持 |
| Trojan | 模仿 HTTPS 的代理 | TLS 承载，密码认证 | 支持 | 支持 | 支持 |
| Hysteria2 | 基于 QUIC 的高带宽代理 | UDP，QUIC，可调拥塞控制 | 支持 | 未列入官方协议文档 | 支持 |
| TUIC | 基于 QUIC 的轻量代理 | UDP，QUIC | 支持 | 未列入官方协议文档 | 支持 |
| WireGuard | 通用 VPN 协议 | UDP，NoiseIK 握手 | 提供出站 | 提供出站 | 支持 |

表中的“支持”只表示官方文档列出了该协议，不构成版本兼容承诺。项目调整协议实现时不会另行通知，以各自文档为准。这张表最实用的地方是排除法，订阅里是 Hysteria2 节点时，先确认客户端内核是否列了这个协议，再去查线路。

### 故障现象与层级

| 现象 | 最可能层级 | 第一个验证动作 | 先不要做 |
| --- | --- | --- | --- |
| 双击后没有反应或闪退 | 安装与运行库 | 在终端启动，读取第一条错误 | 重装系统 |
| 显示已连接但网页打不开 | DNS 或路由 | 直接访问 IP，绕过域名解析 | 逐个换节点 |
| 只有部分应用不走代理 | 接管方式 | 确认该应用是否读取系统代理 | 改分流规则 |
| 启动日志报端口占用 | 本地端口 | 查监听该端口的进程 | 重启电脑 |
| 订阅更新后节点为空 | 订阅解析 | 查看订阅原始响应内容 | 删除全部配置 |
| 所有节点都超时 | 本地网络或出口 | 关闭代理测本地连通性 | 反复导入订阅 |

排查顺序从上往下。先确认进程活着，再确认端口在听，再确认配置能解析，再确认出站握手，最后才怀疑线路和目标站点。跳步的代价是把配置问题当成线路问题，越换越糟。

## 选型决策树

选客户端的标准是三件事，设备权限、订阅格式、使用场景，三者匹配优先于功能数量。下面这棵树按设备分流，最后一层落到动作，走完一遍再下载，能避开大部分返工。

```text
需要给一台设备装代理软件
├─ 第一步，确认设备
│  ├─ Windows
│  │  ├─ 要图形界面与规则分流
│  │  │  ├─ 订阅是 Clash YAML ──────► Mihomo 系 GUI
│  │  │  └─ 订阅含 Xray 专有协议 ──► v2rayN 加 Xray-core
│  │  └─ 要无人值守或脚本调用 ─────► 直接运行内核二进制
│  ├─ Android
│  │  ├─ 订阅是 Clash YAML ────────► FlClash
│  │  ├─ 需要分应用代理 ───────────► v2rayNG
│  │  └─ 订阅是 sing-box JSON ─────► Hiddify 或 NekoBox
│  ├─ iOS
│  │  ├─ 账号所在商店能搜到 ───────► 按客户端支持的格式选
│  │  └─ 搜不到 ───────────────────► 停在这里，只判断机制
│  ├─ macOS
│  │  ├─ 要菜单栏操作 ─────────────► Mihomo 系 GUI
│  │  └─ 要命令行 ─────────────────► 内核二进制加系统代理
│  ├─ OpenWrt
│  │  ├─ 闪存剩余空间足够 ─────────► 插件加内核
│  │  └─ 空间不足 ─────────────────► 外置存储或旁路由
│  └─ Linux
│     ├─ 单机使用 ─────────────────► 内核加环境变量或系统代理
│     └─ 作为网关 ─────────────────► TUN 或 TPROXY 加 nftables
└─ 第二步，回答三个问题
   ├─ 订阅是什么格式 ──────────────► 决定客户端类型
   ├─ 是否需要 UDP ────────────────► 决定系统代理还是 TUN
   └─ 是否愿意授权管理员 ──────────► 决定能否开启 TUN
```

### 三个问题的判断依据

订阅格式可以直接看出来。把订阅链接在浏览器里打开，返回一段可读的 YAML，说明是 Clash 格式；返回一串 Base64，解码后是每行一个 URI，说明是通用链接列表；返回 JSON 且顶层有 outbounds，说明是 sing-box 格式。格式与客户端不匹配时，导入会失败或只导入一部分节点。

是否需要 UDP，取决于你要用的应用。网页、邮件、文件传输以 TCP 为主，系统代理足够。DNS 查询、HTTP/3、游戏、语音通话依赖 UDP，只有 TUN 或 VpnService 能完整接管。判断方法很直接，开系统代理后访问一个只支持 HTTP/3 的站点，若连接退回到 TCP，说明 UDP 没被接管。

是否愿意授权管理员，取决于使用时长与设备归属。公司电脑、共用电脑不适合长期保留提权组件。个人设备且需要 TUN 时，授权是必要代价，但要确认授权对象是哪个组件，是内核服务、虚拟网卡驱动，还是系统扩展。

### 场景与接管方式

| 使用场景 | 接管方式 | 主要代价 | 不适合的情况 |
| --- | --- | --- | --- |
| 浏览器查资料、收发邮件 | 系统代理 | 部分应用不遵循 | 需要接管全部应用 |
| 视频、游戏、语音 | TUN 或 VpnService | 需要提权，改路由表 | 无法授权的共用设备 |
| 全家多设备 | 路由器网关 | 故障影响面覆盖全屋 | 只需要单机临时使用 |
| 临时借用他人电脑 | 便携版或单文件 | 更新需手动，配置不持久 | 长期使用 |

### 换客户端解决不了的四种情况

第一种，订阅本身失效。链接返回 404 或内容为空，换任何客户端都一样。第二种，服务端参数变了。协议、端口、传输方式改动后，旧配置连不上，需要重新获取订阅。第三种，网络层阻断。目标端口或协议特征被拦截，客户端只能换协议或换线路。第四种，目标站点限制。站点按 IP 信誉或地区拒绝请求，本地怎么调都没用。这四种情况的共同点是，问题不在软件层，继续折腾客户端只会浪费时间。

## 底层网络原理

客户端之间的行为差异，最后都能落到几个协议细节上。这一节按数据实际走过的顺序展开，先看一次请求怎样进入隧道，再看传输层、TLS、QUIC、DNS 与 MTU 分别在哪里制造差异。

### 代理握手与数据路径

```text
应用              本地代理端口            内核               远端出口           目标站点
 │  SOCKS5 或 HTTP CONNECT  │                 │                  │                 │
 ├────────────────►│  解析目标，匹配规则     │                  │                 │
 │                 ├────────────────────────►│  建立隧道        │                 │
 │                 │                         ├─────────────────►│  握手与认证     │
 │                 │                         │◄───── 就绪 ──────┤                 │
 │                 │◄─────── 确认 ───────────┤                  ├─ 发起请求 ────►│
 │◄──── 响应 ──────┤◄────────────────────────┤◄─────────────────┤◄────────────────┤
 │                 │                         │                  │                 │
 │   本地段明文     │        隧道段加密        │                  │  端到端连接     │
```

本地段是明文。应用通过 SOCKS5 或 HTTP CONNECT 告诉客户端目标地址，这段通信发生在本机回环接口上，同一台机器上的其他程序可以看到目标域名与端口。隧道段是否加密取决于协议，VLESS 本身不加密，安全性完全来自外层 TLS 或 REALITY。出口到目标是新建连接，访问 HTTPS 站点时，TLS 仍然由应用与站点端到端协商，代理只能看到 SNI 与流量特征。

这段路径解释了两个常见现象。本地端口被占用时，应用报的是连接失败，不是认证失败。隧道握手成功但目标站点拒绝时，日志里是出口侧的错误，不是本地配置错误。

### TCP 与 UDP 的分岔

| 场景 | 传输 | 系统代理能否接管 | TUN 能否接管 | 说明 |
| --- | --- | --- | --- | --- |
| 网页 HTTPS | TCP | 能 | 能 | 依赖应用读取系统代理设置 |
| DNS 查询 | UDP 为主 | 通常不能 | 能 | 需要单独接管解析 |
| HTTP/3 | UDP 443 | 多数不能 | 能 | UDP 受限时回退到 TCP |
| 在线游戏 | UDP | 不能 | 能 | 延迟取决于转发链路 |
| 语音通话 | UDP | 多为直连 | 能 | 部分应用自带中继 |
| 大文件下载 | TCP 多连接 | 能 | 能 | 受带宽与并发数限制 |

TCP 面向连接，三次握手占一个往返，重传与拥塞控制由系统内核处理。UDP 无连接，没有握手与重传，DNS、QUIC、游戏、语音都建立在它之上。系统代理是一份地址设置，只对愿意读取它的应用生效，而多数应用的 UDP 流量根本不查询系统代理。这就是“网页能开、游戏连不上”的技术原因。

### TLS 握手与 SNI

```text
TLS 1.3 over TCP                        QUIC over UDP
客户端              服务器              客户端              服务器
  │ ClientHello       │                  │ Initial(CH)       │
  ├──────────────────►│                  ├──────────────────►│
  │◄─ ServerHello ────┤                  │◄─ Initial(SH) ────┤
  │  Finished         │                  │  Finished         │
  ├──────────────────►│                  ├──────────────────►│
  │◄══ 应用数据 ══════►│                  │◄══ 应用数据 ══════►│
  │   完整握手 1 RTT   │                  │  1 RTT，可 0-RTT   │
```

TLS 1.3 把完整握手压缩到一个往返，会话恢复可以做到 0-RTT，代价是早期数据存在重放风险。ClientHello 里的 SNI 默认是明文，中间设备能看到你访问的域名。ECH 把 SNI 加密后放进外层，需要客户端与服务器同时支持，部署条件较高。

REALITY 走的是另一条路。它借用真实站点的证书链完成握手，客户端看到的是目标站点的证书，代理服务器不持有自己的证书。这种设计减少了证书签发的暴露面，也意味着客户端必须拿到正确的公钥与短 ID，参数抄错时表现为握手直接失败，不会给出“证书不正确”的提示。

### QUIC、Hysteria2 与 TUIC

QUIC 把传输与加密合并到 UDP 上，避免 TCP 的队头阻塞，支持连接迁移。代价是它对 UDP 的依赖，网络对 UDP 限速或阻断时，QUIC 的表现会比 TCP 更差。浏览器通常会回退到 TCP，代理客户端则要看配置是否允许回退。

Hysteria2 与 TUIC 都建立在 QUIC 之上。Hysteria2 提供可调的拥塞控制策略，在高丢包链路上可以换取更高吞吐，但这种策略不参与常规的拥塞退让，与其他流量共存时公平性较差。TUIC 更接近轻量传输，功能面窄一些。两者都要求客户端内核列出对应协议，Xray-core 的官方协议文档中没有这两项，订阅里出现这类节点时需要换内核。

### DNS 解析、fake-ip 与泄漏

```text
redir-host 模式                        fake-ip 模式
应用查 example.com                     应用查 example.com
   │                                      │
   ▼                                      ▼
本地或代理 DNS 返回真实 IP              内核立即返回 198.18.x.x
   │                                      │
   ▼                                      ▼
按 IP 规则分流                          应用连接假地址
   │                                      │
   ▼                                      ▼
连接目标 IP                             内核按域名匹配规则，再解析真实地址
```

redir-host 先解析再分流，规则基于 IP，配置简单，缺点是解析发生在分流之前，域名信息已经丢失，基于域名的规则无法生效。fake-ip 先返回一个保留网段的假地址，等应用发起连接时，内核用域名匹配规则，再解析真实地址。它让域名成为分流的第一依据，代价是部分应用会缓存假地址、部分网络诊断工具显示异常、少数游戏反作弊会拒绝假地址。

fake-ip 需要配置排除列表。局域网设备名、打印机、投屏、部分即时通讯的直连域名，都应该放进 fake-ip-filter，否则这些应用会拿到无法连接的假地址。DNS 泄漏通常来自三条路径，系统解析器没有指向内核、应用自带 DoH 绕过了本地设置、IPv6 解析走了未接管的通道。三条路径要分别验证，只改一条不会消除泄漏。

### MTU、分片与 MSS

以太网 MTU 是 1500 字节，PPPoE 拨号环境是 1492 字节。隧道封装会占掉 20 到 80 字节，TUN 默认继承 1500 时，内层数据包可能超过链路实际承载能力。TCP 会用 MSS 协商单段大小，IPv4 下 1500 减 20 减 20 等于 1460，隧道内通常需要把 MSS 压到 1360 至 1400。

MTU 不匹配的典型症状是小包通、大包卡。ping 能通，DNS 能解析，TLS 握手在 ClientHello 之后没有响应，网页加载到一半停住。验证方法是逐步下调探测包大小，Windows 用 `ping -f`，Linux 用 `ping -M do`，找到能通过的最大值，再加上 28 字节的 IP 与 ICMP 头，就是链路 MTU。

修复顺序是先调 TUN 的 MTU，再配置 MSS clamp，最后才怀疑线路。反过来做，会在一个只需要改一个数字的问题上耗费几个小时。

### 本地端口与回环

本地代理端口默认只监听回环地址，只有本机可以连接。开启局域网访问后，监听地址变成所有网卡，同一网络内的设备都能使用这个出口，也意味着同一网络内的人可以扫描到它。需要共享时，至少配合防火墙规则与认证，不要把一个无认证的开放代理放进公共网络。

端口冲突来自默认值重合。两个客户端都使用 7890 时，第二个启动会在日志里报绑定失败，界面可能仍显示运行中。处理方式是改端口，不是反复重启。改完端口后，系统代理与规则里的旧端口也要同步更新，否则出现“内核在跑、流量不动”的假象。

## 成本模型与预算测算

免费软件的成本不是零，它把许可费转移到了别处。把支出拆成五项，才能判断某个方案是真的省钱，还是把成本换成了时间与风险。

```text
月总成本 = 服务月费 + 设备折旧 + 电费 + 维护时间成本 + 超额流量费
设备折旧 = 设备购置价 ÷ 折旧月数
电费 = 功率(W) × 24 × 30 ÷ 1000 × 电价(元/kWh)
维护时间成本 = 每月维护小时 × 时薪
单位流量成本 = 月总成本 ÷ 月实际用量(GB)
```

公式里的服务月费可以为 0，其余四项不会自动为 0。设备折旧对应路由器、迷你主机或额外硬盘。电费对应常开网关。维护时间对应配置、升级、排障。超额流量费对应超出套餐后的计费。

### 三个测算例子

例一，订阅方案。假设月费 10 元、月用量 100 GB、每月维护 0.5 小时、时薪 60 元。时间成本 30 元，月总成本 40 元，单位流量成本 0.40 元/GB。忽略时间成本时是 0.10 元/GB，差了四倍。这个例子说明，低月费方案的单位成本对维护时间极其敏感。

例二，自建方案。假设服务器 5 美元/月、汇率 7.2，折合 36 元。月用量 200 GB 时单位成本 0.18 元/GB；月用量 40 GB 时升到 0.90 元/GB。加上每月 2 小时维护，成本增加 120 元，两种用量下的单位成本分别变成 0.78 元/GB 与 3.90 元/GB。自建的优势在用量大且维护熟练时成立，用量小的时候比订阅贵。

例三，路由器网关。假设二手路由器 200 元、折旧 24 个月，每月 8.33 元；功耗 6 W、电价 0.6 元/kWh，每月电费 2.59 元；首次配置 3 小时、时薪 60 元，按 12 个月摊销，每月 15 元。月总成本 25.92 元。三台设备分摊后每台 8.64 元。设备越多，单台成本越低，但故障影响面也越大。

### 测算假设表

| 假设项 | 取值 | 单位 | 说明 |
| --- | --- | --- | --- |
| 汇率 | 7.2 | 元/美元 | 仅用于把外币报价折算成人民币 |
| 时薪 | 60 | 元/小时 | 按个人时间的机会成本估算 |
| 设备折旧 | 24 | 月 | 消费级路由器的常见更换周期 |
| 网关功耗 | 6 | 瓦 | 不含无线射频时的估算值 |
| 电价 | 0.6 | 元/千瓦时 | 居民用电的常见档位 |
| 月用量 | 40 至 200 | GB | 覆盖轻度到中度使用 |
| 维护时间 | 0.5 至 3 | 小时/月 | 含配置、升级与排障 |

这张表的所有取值都是测算假设，不是市场报价，也不是实测数据。换一个时薪或汇率，结论会变。把假设写出来，读者才能按自己的情况重算。

### 免费软件免掉了什么

许可费确实免了。Mihomo、Xray-core、sing-box 都是开源项目，源码可查，发布包可下载，不需要付费授权。这一项在总成本里占比通常最小。

服务器没有免。内核只负责把流量送出去，出口服务器由服务方提供，或者由你自己租用。订阅费、VPS 费用、专线费用都属于这一项。

时间没有免。配置、升级、排障、迁移都要占用时间，而时间有价格。一个月维护两小时，按 60 元时薪计算就是 120 元，超过多数低价订阅的月费。

风险没有免。来源不明的安装包、权限过大的客户端、泄露的订阅链接，都会带来重置成本。这类成本不常发生，一旦发生就很高。

### 什么时候免费软件反而更贵

三种情况。第一，维护时间超过订阅价格。第二，多设备重复配置，每台设备各调一遍，边际成本没有下降。第三，安装包来源不可核验，为了确认安全性投入的检查时间超过软件本身的价值。

判断方法很简单，把上个月的维护时间记下来，乘以自己的时薪，再和同期的订阅支出比较。时间成本更高时，付费买省心是理性选择；时间成本更低且愿意折腾时，继续用开源方案也合理。这个判断不需要道德立场，只需要算术。

## 核验方法与可复现条件

核验要回答三个问题，“我下载了什么、它来自哪里、它有没有被改过”。它不能证明某个软件绝对安全，但能让这三个问题都有证据，证据还要能被他人复现。

### 三步核验

第一步核来源。打开项目主页，确认组织归属、仓库名与 README 里给出的官方文档域名一致。从仓库进入 Releases 页面，检查资产文件名是否对应你的平台与架构。页面上出现的下载按钮如果指向第三方域名，直接放弃。

第二步核完整性。下载同页面的校验和文件，对安装包计算 SHA-256 并比对。项目提供签名时，先验证签名，再安装。校验和文件本身也必须来自同一个发布页，从别的页面拿到的校验和没有意义。

第三步核行为。安装后观察三件事，内核监听了哪些端口，客户端向哪些地址发起更新检查，系统代理或路由表被改成了什么。三项都能在系统工具里看到，不需要抓包也能完成基础判断。

### 证据清单

| 证据 | 采集位置或命令 | 单位 | 复现条件 |
| --- | --- | --- | --- |
| 发布页地址 | 浏览器地址栏 | 条 | 记录访问日期 |
| 资产文件名 | Release 页面 | 个 | 记录版本标签 |
| SHA-256 | Get-FileHash 或 sha256sum | 64 位十六进制 | 下载完成后立即计算 |
| 签名主体 | Get-AuthenticodeSignature 或 codesign | 主体名称 | 安装前验证 |
| 监听端口 | netstat 或 ss | 端口号 | 内核启动后 |
| 系统代理值 | 系统设置或注册表 | 键值 | 开启接管后 |
| 日志行 | 客户端日志目录 | 行 | 复现故障的同一操作 |

### 命令清单

```text
Windows PowerShell   Get-FileHash .\client.exe -Algorithm SHA256
Windows CMD          certutil -hashfile client.exe SHA256
macOS                shasum -a 256 client.dmg
Linux                sha256sum client.AppImage
Android              apksigner verify --print-certs client.apk
macOS 签名           codesign -dv --verbose=4 /Applications/Client.app
macOS 公证           spctl -a -vv /Applications/Client.app
```

命令只做一件事，把文件内容变成一个固定长度的摘要。摘要一致，说明文件与发布页声明的一致；摘要不一致，说明下载被替换或文件损坏。摘要一致不代表软件没有漏洞，它只回答完整性问题。

### 可复现条件

记录五件事，核验时间、操作系统版本、客户端版本、内核版本、配置摘要。缺一项，结论就无法被他人复现。时间要写到日，版本要写到发布标签，配置摘要可以是文件哈希，也可以是关键字段的截图。

本站的核验口径写在资源检测专题的方法一节，包含采样次数、单位与证据格式。代理软件的核验不涉及速度测试，但同样要求时间、环境与证据三要素齐全。没有这三要素的结论，只能算个人印象。

### 常见核验误区

第一个误区，把“能打开官网”当成来源可靠。仿冒站点的页面可以做得一模一样，真正的判断依据是域名归属与下载链接指向。

第二个误区，只比对文件大小。大小可以伪造成一致，哈希不行。

第三个误区，验证了签名就认为万事大吉。签名只证明发布者身份，不证明代码没有漏洞，也不证明发布者可信。

第四个误区，用在线哈希网站处理安装包。把文件上传到第三方站点，等于把样本交给了未知方，安装包本身可能包含账号信息或配置。

## 安全、隐私与合规边界

代理软件同时扮演两个角色，本机的高权限组件，以及流量的中间人。两个角色都会扩大攻击面，所以安全讨论要分开看，软件本身的风险与服务端的风险不是一回事。

### 威胁模型

| 威胁 | 触发条件 | 影响 | 降低手段 | 残留风险 |
| --- | --- | --- | --- | --- |
| 安装包被替换 | 从聚合下载站获取安装包 | 任意代码执行 | 官方 Release、哈希、签名三重核对 | 官方账号或构建环境被攻破 |
| 供应链投毒 | 依赖包或构建流程被修改 | 后门、数据外传 | 固定版本、比对哈希、关注安全公告 | 无法在本地完整复现构建 |
| 本地端口暴露 | 开启局域网访问且无认证 | 他人借用出口，行为记在你名下 | 关闭局域网访问，防火墙限制来源 | 同机恶意程序读取回环端口 |
| 订阅链接泄露 | 截图、剪贴板、同步笔记、公开求助 | 额度被盗用，身份被关联 | 当作密码管理，定期重置 | 服务端仍保留使用记录 |
| DNS 泄漏 | 系统解析器绕过代理，应用自带 DoH | 访问记录暴露给本地网络 | TUN 加 DNS 接管，逐条验证解析路径 | 应用内置解析无法完全拦截 |
| 权限过度 | 长期保留管理员或系统扩展 | 内核漏洞影响整机 | 按需提权，用完撤销 | 内核自身漏洞 |
| 更新通道被劫持 | 客户端从非官方地址取更新 | 持久化后门 | 只从官方发布页更新，核对下载域名 | 域名劫持与证书错误被忽略 |

### 威胁模型怎么用

七个威胁不需要同时防。先看可能性，再看影响。个人设备上最可能发生的是安装包被替换与订阅泄露，两者都能用低成本手段降低。供应链投毒的影响更大，但个人用户能做的有限，固定版本与关注公告已经是合理范围。企业环境里，权限过度与更新通道是重点，因为设备数量放大了单点失败的后果。

### 加密不等于匿名

TUN 模式把流量送进隧道，隧道只加密到出口。出口之后的连接由出口服务器发起，目标站点看到的是出口地址。链路上的中间人看不到内容，但能看到你在什么时间连接了哪个地址，TLS 握手中的 SNI 默认也是明文。

匿名性还会被账号体系打破。用同一个账号登录多个服务，出口 IP 再换也无法消除关联。DNS 请求、浏览器指纹、时区与语言设置，都能提供额外的识别信息。代理软件解决的是可达性问题，不解决身份问题，这一点在任何配置下都成立。

### 本地端口与局域网暴露

本地代理端口默认监听回环地址，只有本机能连。开启局域网共享后，监听地址变成所有网卡，同一网络里的设备都能把它当出口使用，也能扫描到它的存在。家庭网络里这通常可以接受，公共网络里等于开放了一个无认证代理。

需要共享时，至少做三件事，限制来源地址段、设置认证、在防火墙上只放行必要端口。三件事都做完，仍然要接受一个事实，通过这个端口的流量会与你的出口地址绑定，他人的行为可能被记在你名下。

### 日志、订阅与截图

客户端日志默认会记录连接目标、时间、命中的规则，排障时非常有用，分享时非常危险。把日志贴到公开 issue 或论坛前，先删掉域名、IP、订阅地址与账号标识。规则命中日志同样会暴露访问习惯。

订阅链接本身就是凭据。它通常包含账号令牌，拿到链接就能拉取节点列表并消耗额度。截图时遮住链接，不要把订阅写进云笔记的公开分享，也不要用同一个链接在多个陌生设备上反复导入。

### 权限最小化

Windows 上的 TUN 需要管理员权限或一个以服务方式运行的内核，macOS 上需要 helper 或系统扩展，Android 上需要 VpnService 授权，iOS 上需要 Network Extension。这些授权都有明确用途，判断标准是它是否只在需要时存在。

可执行的做法有三条。不用 TUN 时切回系统代理并撤销提权。关闭客户端后检查服务是否仍在运行。系统更新后重新确认扩展与授权状态，更新有时会重置这些设置。

### 合规边界

不同司法辖区对代理工具的规定不同，使用前自行确认当地法律、服务条款与可接受使用政策。本页不提供规避执法、规避实名制或绕过企业网络管理的操作指南。企业设备与公司网络先看 IT 政策，个人设备也要看所访问服务的使用条款。

软件开源、协议公开，不代表使用场景自动合规。判断依据是当地规则与服务条款，不是软件许可证。

## 分类地图

八个二级分类按一条主线排列，先按设备找客户端，再回到来源与权限，最后处理配置与维护。每个分类下的集群都指向一个可独立回答的问题，不是关键词的排列组合。

### Windows 客户端

覆盖 Mihomo 系与 Xray 系两条线。重点在 GUI 与内核的分离、配置目录、服务模式与端口冲突。Windows 的复杂度主要来自权限与系统代理接口，不是协议本身。

### Android 客户端

以 v2rayNG 与 FlClash 为主，附带 NekoBox 与 Hiddify 的定位比较。核心概念是 VpnService 授权、单实例限制、分应用代理与后台省电策略。安卓端的问题多数能在系统设置里找到答案。

### Apple 客户端

iOS 与 macOS 分开处理。iOS 的重点是商店地区、TestFlight 机制、Network Extension 的能力边界；macOS 的重点是公证、helper 授权、Apple 芯片构建与睡眠唤醒后的重连。这一分类只解释机制，不给购买建议。

### 路由器与 Linux

OpenWrt 与 Linux 网关放在一起，因为两者都要处理透明代理、DNS 接管与防火墙规则。差别在工具链，OpenWrt 用 opkg 与 LuCI，Linux 用包管理器与 systemd。共同点是故障影响面大，配置前要留好回退路径。

### 官方来源与版本

这一分类回答“从哪里下载”。GitHub Release 的资产命名、latest 与预发布标签、fork 与镜像的区分、假官网的识别，都属于发布页阅读能力。它不提供版本号承诺，只提供判断方法。

### 权限与隐私

系统代理与 TUN 的差异、TUN 的路由改写、VPN 权限的真实含义，都集中在这里。权限决定了软件能做什么，也决定了出问题时影响多大。理解这一层，才能判断某个授权请求是否合理。

### 配置与订阅

从订阅链接到可用规则。四种订阅载荷、格式转换、更新策略、规则顺序、DNS 分流、fake-ip 的行为，都属于这一层。配置问题的特点是现象明确、原因隐蔽，需要按日志逐条验证。

### 更新与故障

版本错配、通道选择、配置迁移、回滚、分层排查。维护阶段的目标是在可控范围内保持可用，追新排在后面。故障排查的顺序在参数表一节已经给出，这一分类展开每一步的具体做法。

## 常见问题

### 免费代理软件是不是就不用花钱了

软件许可确实不花钱，服务器、设备、时间与风险仍然有成本。内核开源不等于出口免费，订阅费或服务器租金是另一笔支出。以测算假设为例，月费 10 元、每月维护半小时、时薪 60 元，时间成本就是 30 元，达到月费的三倍。把这几项加起来才是完整成本，单看软件标价容易得出错误结论。订阅到期后额度归零，这笔支出不会因为客户端开源而消失。

### 客户端和内核必须成对使用吗

不必须，但要匹配。GUI 生成配置并调用内核，只要配置字段被内核识别，跨项目组合也能工作。风险在版本与字段，GUI 更新了而内核没更新时，新字段会被忽略或直接报错；反过来，新内核遇到旧 GUI 生成的配置，可能启动失败。跨项目组合出问题时，先分别记录 GUI 与内核版本，再对照发布说明查字段变更。版本信息在客户端的关于页面与内核的版本输出里都能看到。

### 从 GitHub 下载的安装包就一定安全吗

不一定。GitHub 只保证托管，不保证每个仓库的代码质量与发布流程。判断依据是仓库归属、发布者身份、校验和与签名是否齐全。项目维护者账号被盗后发布带后门安装包的事件真实发生过，下载量与收藏数都不能当作安全证据。下载后仍要核对 SHA-256，项目提供签名时先验签，条件允许时比对源码构建结果。

### 系统代理和 TUN 应该选哪个

看应用是否读取系统代理，以及是否需要 UDP。只浏览网页时系统代理足够，不用提权，退出即恢复，适合共用电脑。需要游戏、语音、HTTP/3 或某些不读系统设置的应用时，用 TUN 或 VpnService。两者差别不在速度快慢，而在覆盖范围与权限代价，TUN 会改写路由表，出问题时表现为整机断网，不再局限于单个应用。先确定需要接管哪些流量，再挑客户端，顺序不要反过来。

### 手机上开代理会影响银行类应用吗

可能影响。部分银行与支付应用会检测 VPN 或代理环境，触发风控或直接拒绝启动，这类检测属于应用自身的策略，客户端无法保证兼容。用分应用代理把这些应用排除，通常能缓解。排除后它们走本地网络，仍受当地网络环境影响。遇到登录异常时先关闭代理重试，再判断问题在应用风控还是网络。分应用清单里同时保留系统框架应用，避免通知与推送异常。

### iOS 上为什么搜不到某些客户端

App Store 的可见性由账号所属商店地区决定，开发者也可以选择只在部分地区上架。应用被下架后，已购记录与更新通道都会受影响，能否重新下载取决于购买记录与当前商店状态。TestFlight 是另一条分发路径，有测试名额与有效期限制，到期后需要新的构建。本页只解释机制，不讨论切换账号地区的操作。商店可见性也会随地区与时间变化，这里不构成购买建议。

### 订阅链接可以发给别人吗

不建议。订阅链接通常包含账号令牌，拿到链接就能拉取节点并消耗额度，部分服务还会把它与支付信息关联。截图、剪贴板同步、公开求助帖、浏览器同步都是常见泄露路径。需要共享时，先确认服务条款是否允许，再使用服务方提供的独立分享机制。确认泄露后尽快重置链接，并检查用量是否异常。

### 客户端提示版本不兼容怎么办

先记录三个版本，客户端、内核、订阅格式。对照发布说明确认字段变更，再用内核自带的配置校验命令验证文件，校验通过再启动。多数不兼容来自内核新增或移除字段，回退到上一个可用版本通常比逐行改配置更快。回退后保留旧安装包与旧配置，每次升级前备份一份可用配置，避免重复排查。

### 路由器上装代理插件值不值得

设备多、长期开、愿意维护时值得。一次配置覆盖全屋，单台成本随设备数下降，按测算假设三台设备分摊后每台约 8.64 元。代价是故障影响面覆盖所有设备，固件升级可能丢配置，闪存空间有限。只有一两台设备且不常看视频时，桌面客户端加手机客户端更简单，排查也更快。决定前先数设备数量与观看时长，再算成本。

### 开了 TUN 之后 IPv6 还能用吗

取决于是否接管 IPv6 路由与解析。只接管 IPv4 时，IPv6 流量会绕过代理直连，出现部分站点走代理、部分直连的现象，也可能暴露真实地址。三条处理路径是禁用 IPv6、把 IPv6 路由也指向虚拟网卡、或在 DNS 层不返回 AAAA 记录。选哪条取决于本地网络是否真的支持 IPv6，盲目禁用可能影响只提供 IPv6 的服务。改动后分别用 IPv4 与 IPv6 测试站点确认接管范围。

### 客户端停止维护了要马上换吗

不必马上，但要有迁移计划。停更客户端的风险来自未修复的漏洞与协议变化，短期仍可用，长期会逐渐失效，尤其是服务端启用新传输方式之后。迁移时先导出配置与规则，确认新客户端支持订阅里的全部协议，再切换。切换后保留旧客户端与旧配置一段时间，出现问题时可以回退。评估标准是能否覆盖现有设备与协议，价格排在后面。
