# 资源检测

> 直接结论：一个节点是否可用，要分开回答四个问题，TCP 能否握手、代理协议能否完成认证、通过它能否取回目标内容、在指定时间窗内能否重复。四次都通过，带宽与解锁才有讨论价值。本页给出判定顺序、采样参数、单位换算与记录格式，文中所有数值均为示例数据，非实测。

## 直接结论与适用边界

判断一个节点要按四个层次分开回答，任何一层失败，后面的数字都没有意义。

每个检测数字都要带三样东西，单位、条件、时间。延迟写毫秒时要说明是 ICMP 往返、TCP 握手还是首字节；带宽写 Mbps 时要说明单线程还是多线程、持续多少秒、目标端点在哪个地区；丢包写百分比时要说明发了多少个包、在哪个时间段、用哪种协议探测。缺一样，这个数字只能当参考，不能进对比表。

检测顺序有物理依据。TCP 握手是最外层的可达性，失败原因最容易误判。代理握手依赖认证、时间同步与协议版本。端到端取回要穿过目标站点的 CDN 与风控。应用层判定还要叠加账号状态与地区库。顺序颠倒会把目标站点的拒绝记成节点故障。

本页不推荐具体机场或节点，不评价服务优劣，只给判定条件与记录格式。不同司法辖区对代理服务与内容访问的规则不同，使用前需自行确认当地法律、服务条款与可接受使用政策。

时间会改变结论。同一条线路在 20:00 到 23:00 的往返时间中位数可能比 10:00 高出数十毫秒，跨境链路在拥塞时段的丢包率会抬升。检测报告必须带时间戳与时区，跨日期比较要说明是否处于同一时间窗。版本同样会改变结果，客户端内核升级、规则集更新、DNS 配置变化都会让旧数据失效。

### 不回答什么

第一，不判断某家机场是否值得购买。这需要主体信息、条款、支付与退款记录，超出检测范围。

第二，不承诺任何免费额度存在。本站当前收录的合格免费资源为 0 条，零结果的含义是没有可复核条目，与全网是否存在无关。

第三，不给“哪个节点最快”的排名。速度依赖时间窗、目标端点与本地带宽，脱离条件的排名无法复核。

第四，不提供自动化绕过风控的方法。涉及验证码、设备指纹与账号关联的部分，只说明观测方法与风险边界。

第五，不解释如何隐藏检测行为。检测应当遵守目标服务的使用条款，高频探测可能触发限流，这本身会影响结果。

## 概念与实体关系

### 十二个实体

检测对象可以拆成十二个实体。分开命名是为了让每个指标找到唯一归属，避免把客户端显示的数字当成线路表现。

| 实体 | 定义 | 观测方式 |
| --- | --- | --- |
| 节点 node | 一组可连接的服务器参数，含地址、端口、认证与传输配置 | 订阅解析、客户端列表 |
| 订阅 subscription | 节点集合的更新载体，格式可能是 Base64、Clash YAML 或 sing-box JSON | 拉取响应、解析结果 |
| 客户端 client | 提供界面、系统代理、TUN 与规则管理的程序 | 版本号、日志、配置导出 |
| 内核 core | 实际实现协议、加密与转发的进程 | 版本号、启动参数、运行日志 |
| 代理协议 protocol | Shadowsocks、VMess、VLESS、Trojan、Hysteria2、TUIC 等 | 配置字段、握手日志 |
| 传输层 transport | TCP、TLS、QUIC、WebSocket、gRPC 等承载方式 | 抓包、端口与 ALPN |
| 出口 IP exit IP | 目标站点观察到的源地址 | 回显服务、HTTP 头、日志 |
| DNS 解析器 resolver | 把域名解析成地址的服务，可能是本地、运营商或加密解析器 | dig 查询、客户端 DNS 日志 |
| 目标服务 target | 网页、流媒体、AI 服务、软件更新源等被访问对象 | 状态码、播放统计、接口响应 |
| 探测点 probe | 执行测量的设备与其接入网络 | 本地基线、路由表、网卡信息 |
| 时间窗 window | 采样覆盖的起止时间与时区 | 时间戳、采样计划 |
| 指标 metric | RTT、抖动、丢包率、吞吐、可用率等可计算量 | 原始样本与统计结果 |

### 三个常见混淆

第一个混淆是把“在线”当成“可用”。客户端列表里的绿色延迟通常来自一次 TCP 连接或一次 HTTP 请求，只证明那个瞬间有一次握手成功。节点可能在握手后立刻断开，可能只允许连接特定端口，也可能在认证阶段拒绝请求。可用性至少要包含握手、认证、取回三段证据。

第二个混淆是把客户端显示的延迟当成端到端延迟。客户端显示的常是到节点入口的 TCP 握手时间。它与打开网页的耗时之间，还差着隧道内往返、目标建连、TLS 协商和服务器处理。跨境链路上，入口延迟 40 毫秒而网页首字节 900 毫秒属于常见组合。

第三个混淆是把出口 IP 的国家当成解锁能力。流媒体与 AI 服务除了看国家，还看 IP 类型、ASN、历史滥用记录、账号注册地和支付地区。同一个国家的两个地址，一个能播放，一个提示地区限制，这种情况在共享地址池里很常见。出口 IP 只是必要条件之一。

### 读表的四条规则

第一，门槛只是判定示例。20 Mbps 对网页浏览够用，对 4K 播放偏紧。门槛跟着用途走，报告里要写用途。

第二，单位必须带方向。下行 100 Mbps 与上行 100 Mbps 是两种线路，低价套餐常只保证下行。只写“100 兆”属于无效描述。

第三，采样口径决定可比性。10 次与 200 次采样得到的 P95 不可直接比较，间隔 0.2 秒与 5 秒的抖动也不可比。

第四，数据性质分三类。单次快照只说明瞬间，分布统计需要样本量与分位算法，布尔判定需要写清条件。混在一张表里，读者会误以为精度相同。

### 数据性质分类

| 性质 | 典型指标 | 可支持的结论 | 不可支持的结论 |
| --- | --- | --- | --- |
| 单次快照 | 一次握手、一次解析 | 此刻可达 | 长期可用 |
| 分布统计 | P50、P95、抖动、丢包 | 一段时间内的典型表现 | 峰值体验 |
| 布尔判定 | 可播放、可登录 | 在特定账号与地区下成立 | 普遍解锁能力 |
| 累计比率 | 可用率、成功率 | 观察期内的稳定程度 | 未来故障概率 |

### 参数之间的耦合

指标之间不独立。往返时间上升会压低单线程吞吐，因为接收窗口填满后必须等待确认；丢包上升会触发拥塞控制降速，让吞吐出现锯齿。检查顺序是先看往返时间与丢包，再看单线程吞吐，最后看多线程吞吐。往返正常而单线程低，优先怀疑窗口与中间设备；单线程正常而多线程上不去，优先怀疑本地带宽或探测点 CPU。

## 分项检测口径

大表给的是横向对比，这一节给每一项的做法与失败信号。阈值仍为示例，方法可以直接照做。

### ICMP 与 TCP 延迟的偏差

ICMP 回显由设备控制面处理，优先级通常低于转发面，遇到限速时延迟抬高，严重时直接丢弃。TCP 握手由内核协议栈处理，路径更接近真实应用。节点禁用 ICMP 时，ping 全部超时，TCP 握手却正常，这类节点不能判为不可用。

两种探测的差值有诊断价值。差值长期超过 100 毫秒，说明 ICMP 被区别对待，应只信 TCP 结果。采样间隔取 0.2 秒到 1 秒，间隔过小会让队列堆积，把排队延迟算进往返时间。

### 抖动与丢包的采样

抖动用相邻往返差值的平均绝对值：

```text
J = 1/(n−1) × Σ|RTT_i − RTT_(i−1)|
```

这个定义与 RTP 的平滑抖动估计不同，报告里要写清用的是哪一种，否则两组数字无法比较。采样 100 个包，间隔 1 秒，晚高峰单独统计。中位数 10 毫秒、P95 40 毫秒，说明大部分时间平稳但存在尖峰。

丢包率的分母是发出的包数。ICMP 限速会制造假丢包，表现为固定比例丢失而 TCP 吞吐正常。判定丢包要看 TCP 重传与应用层超时是否同时出现，单看 ICMP 不够。

### 单线程与多线程的分层

单流吞吐受带宽时延积限制：

```text
BDP = 带宽 × 往返时间
单流上限 ≈ 接收窗口 ÷ 往返时间
```

按 100 Mbps、往返 200 毫秒计算，BDP 为 20 Mbit，即 2.5 MB。接收窗口若只有 256 KiB，单流上限约为 256×1024×8÷0.2，等于 10.5 Mbps。窗口扩大到 4 MiB，上限升到 167.8 Mbps。同一节点在不同设备上速度差异巨大，原因常在这里。

多线程测试按 1、2、4、8、16 的阶梯增加并发，观察吞吐在哪一档饱和。饱和之前的增长来自窗口不足，饱和之后的上限通常来自本地带宽、节点限速或 CPU。测试前先测直连基线，基线不达标时，隧道数据没有解释力。

### 出口 IP 与 ASN 的判定

出口查询至少用三个独立来源，包括 HTTP 回显服务、DNS 查询出口与公开路由数据。三者一致时记录 IP、ASN、国家与查询时间。出现分歧时，优先相信路由数据与延迟估算，地理数据库可能滞后数周。

ASN 类型决定目标服务的初始信任。运营商地址与机房地址在风控系统里的权重不同，机房地址更容易触发验证。记录时写清 ASN 编号与类型，不要只写国家。

IPv6 是常见漏洞。客户端启用双栈而规则只代理 IPv4 时，部分流量会走原生 IPv6，出口与预期不符。检测时分别查 IPv4 与 IPv6 的出口，两者不一致就记录为部分泄漏。

### DNS 泄漏的判定顺序

第一步确认查询由谁发出，是系统解析器、客户端内置解析器还是浏览器自带解析。第二步查解析器的出口地址，用专门的回显查询完成。第三步把解析器出口与节点出口的国家、ASN 比对。第四步区分分流直连与意外泄漏，前者是设计行为。第五步检查 IPv6 与加密 DNS 是否绕过了预期路径。

顺序颠倒会把分流当成泄漏，也会把解析器缓存当成污染。每一步都记录原始输出与时间，否则无法复现。

### 流媒体与 AI 服务的判定层次

流媒体按四步判定，打开首页、搜索目标片源、播放 60 秒、读取播放统计。播放统计里的分辨率、码率、丢帧与缓冲次数比“能打开”更有信息量。4K 片源的常见码率在 15 Mbps 到 25 Mbps 区间，随编码与片源变化，属于量级参考。

AI 服务按四层判定，打开首页、完成登录、提交一次请求、连续使用十分钟。验证码出现在哪一层要单独记录，它可能来自 IP 信誉，也可能来自行为特征。只通过首页就写“可用”，结论强度不足。

两类检测都要写明账号状态、地区设置与时间。同一个出口在登录前后可能给出不同结果。

### 单位换算的三个陷阱

第一个是比特与字节。Mbps 除以 8 得到 MB/s，100 Mbps 等于 12.5 MB/s。

第二个是十进制与二进制。1 GB 等于 10⁹ 字节，1 GiB 等于 2³⁰ 字节，1 GiB 是 1 GB 的 1.0737 倍。100 GB 等于 93.13 GiB。部分系统把 GiB 标成 GB，读数会差 7%。

第三个是平均值与分位数。平均 50 毫秒可能由 45 毫秒的多数样本与 500 毫秒的少数尖峰构成，P95 会直接暴露尖峰。报平均值时必须同时报分位数与样本量。

## 检测判定树

判定树固定排查顺序。同一层不要同时改两个变量，否则无法归因。每层设超时，超时即视为失败并记录。

```text
起点：拿到一个节点，先记录时间、时区、客户端与内核版本、本地网络类型
│
├─ L1  TCP 握手在 3 秒内成功？
│   ├─ 否 ──► 查解析结果是否为空或异常 ──► 查端口是否被本地防火墙拦
│   │          ──► 查入口地址是否可达（换探测点复测一次）
│   │          结论：不可达。记录超时值、解析地址、目标端口
│   └─ 是
│       │
│       ├─ L2  代理协议握手成功？
│       │   ├─ 否 ──► 读内核日志：认证失败 / 时间偏差 / 协议不支持
│       │   │          结论：配置层失败，与线路质量无关
│       │   └─ 是
│       │       │
│       │       ├─ L3  通过代理取回目标，状态码为 2xx 或 3xx？
│       │       │   ├─ 否 ──► 403 或 429：目标侧风控
│       │       │   │          502 或 504：出口或上游异常
│       │       │   │          超时：查 MTU、丢包与 DNS
│       │       │   │          结论：先分层归因，再决定是否换节点
│       │       │   └─ 是
│       │       │       │
│       │       │       ├─ L4  性能是否达到用途要求？
│       │       │       │   ├─ 延迟与抖动：20 次采样，报 P50 与 P95
│       │       │       │   ├─ 吞吐：先单线程 30 秒，再多线程 8 流
│       │       │       │   └─ 应用层：播放 60 秒，或完成一次登录
│       │       │       │      结论：带单位、条件、时间写入记录
```

### 每层要留的证据

| 层级 | 观测对象 | 常见假设 | 下一步动作 | 证据形式 |
| --- | --- | --- | --- | --- |
| L1 | TCP 握手耗时与结果 | 入口封锁、端口错误、DNS 解析失败 | 换探测点复测，核对解析地址 | 命令输出与时间戳 |
| L2 | 协议握手与认证 | 密码错误、时间偏差、协议版本不支持 | 对齐系统时间，核对配置字段 | 内核日志片段 |
| L3 | 状态码与响应头 | 目标风控、上游故障、MTU 黑洞 | 换目标站点交叉验证 | 响应头与状态码 |
| L4 | 延迟、抖动、吞吐 | 本地瓶颈、链路拥塞、节点限速 | 先测基线，再做对照 | 采样原始数据 |

### 三条使用规则

一次只改一个变量。换节点的同时换客户端版本，结果无法归因。固定客户端与配置，只切换节点，连续测三轮。

失败也要记录。超时值、错误码、日志行数都是证据。只写“失败”两个字，等于放弃了下一次比较的基准。

区分“这次失败”与“这个节点不行”。单次失败可能是本地网络抖动、目标站点维护或临时封锁。判定为不可用之前，至少要有两个不同时间窗的失败记录，间隔不小于 30 分钟。

### 判定树的适用边界

判定树假设读者能拿到内核日志与命令行输出。移动端证据有限，Android 可读应用内日志，iOS 通常只有连接状态与部分统计，L3 与 L4 仍可通过浏览器完成。账号层面的问题，例如登录失败、订阅过期、设备数超限，属于服务侧状态，应先确认账号再进入网络排查。

## 底层网络协议原理

### 一次首字节请求的时间账

以 HTTPS 网站为例，流量经过本地代理内核、节点入口、节点出口，最后到达目标站点。下图按时间顺序展开一次请求，箭头方向表示数据流向。

```text
客户端            本地内核              节点入口/出口           目标站点
  │                  │                      │                    │
  │ 1 CONNECT 请求    │                      │                    │
  ├─────────────────►│                      │                    │
  │                  │ 2 代理协议握手与认证  │                    │
  │                  ├─────────────────────►│                    │
  │                  │ 3 隧道建立确认        │                    │
  │ 4 200 Established│                      │                    │
  │◄─────────────────┤                      │                    │
  │ 5 隧道内 TCP SYN（端到端）                │                    │
  ├──────────────────┼─────────────────────►┼───────────────────►│
  │                  │                      │ 6 SYN-ACK          │
  │◄─────────────────┼──────────────────────┼────────────────────┤
  │ 7 TLS ClientHello（含 SNI）              │                    │
  ├──────────────────┼─────────────────────►┼───────────────────►│
  │                  │                      │ 8 ServerHello 等   │
  │◄─────────────────┼──────────────────────┼────────────────────┤
  │ 9 HTTP 请求       │                      │                    │
  ├──────────────────┼─────────────────────►┼───────────────────►│
  │                  │                      │ 10 响应首字节      │
  │◄─────────────────┼──────────────────────┼────────────────────┤
```

把这张图翻译成公式，首字节时间可以近似写成：

```text
T_first_byte ≈ T_dns + 1×RTT_entry + 1×RTT_tunnel
              + 2×RTT_target + T_server

RTT_tunnel ≈ RTT(客户端→节点) + RTT(节点→目标)
```

公式中的每一项都有对应观测手段。T_dns 用 dig 或客户端日志测量，RTT_entry 用 tcping 测入口，RTT_tunnel 是端到端往返，T_server 由目标站点决定，无法通过换节点改善。这个分解能解释一种常见现象：入口延迟只有 40 毫秒，首字节却接近 900 毫秒。

### TCP 与拥塞控制的可见影响

TCP 三次握手消耗一个往返，之后才能发送数据。握手完成不等于链路健康，窗口与丢包恢复都会影响后续传输。

初始拥塞窗口按公开规范可以设为 10 个最大报文段，粗算约 14.6 KB。窗口扩大选项可以让接收窗口达到数兆字节，实际值由操作系统自动调整，这也是同一节点在不同设备上速度不同的原因之一。

丢包对吞吐的影响是非线性的。拥塞控制把丢包当作拥塞信号时会减半窗口，恢复需要若干往返。百分之一的随机丢包足以让长肥链路的吞吐下降一个显著比例，短链路几乎无感。检测报告里把丢包率与往返时间分开写，读者才能判断影响程度。

### TLS 与 QUIC 的握手差异

TLS 1.3 的完整握手消耗一个往返，会话恢复可以做到零往返。TLS 1.2 的完整握手通常消耗两个往返。握手往返次数直接进入首字节公式，所以同一节点在支持 TLS 1.3 的客户端上通常更快。

QUIC 把传输握手与 TLS 1.3 合并，首次连接一个往返，恢复连接可以零往返。它以 UDP 为载体，在传输层实现多路复用，单一流丢包不会阻塞其他流。代价是部分网络对 UDP 限速或直接封锁，UDP 443 不通时需要用 TCP 回退。基于 QUIC 的代理协议在 UDP 受限网络里表现会明显变差，这与节点带宽无关。

```text
TCP + TLS 1.3               QUIC
┌──────────────┐            ┌──────────────┐
│ SYN          │            │ Initial      │
│ SYN-ACK      │ 1 RTT      │ Handshake    │ 1 RTT
│ ACK          │            │ 1-RTT 数据   │
├──────────────┤            ├──────────────┤
│ TLS 握手     │ 1 RTT      │ 流 0 流 1 流 2│ 独立复用
├──────────────┤            ├──────────────┤
│ HTTP 请求    │            │ 连接 ID 迁移 │ 换网不断线
└──────────────┘            └──────────────┘
```

### 代理协议握手

不同代理协议的握手成本不同，失败信号也不同。检测时应先确认协议类型，再读对应日志。

```text
SOCKS5
客户端 → 05 01 00            （版本 5，一种认证方式：无认证）
服务端 → 05 00               （选择无认证）
客户端 → 05 01 00 03 len host port   （CONNECT，域名类型）
服务端 → 05 00 00 01 ip port          （成功，返回绑定地址）

HTTP CONNECT
客户端 → CONNECT host:443 HTTP/1.1
服务端 → HTTP/1.1 200 Connection Established
```

Shadowsocks 的 AEAD 模式没有显式握手，首个数据包携带盐值，双方用盐值派生会话密钥，之后每个分块带长度与认证标签。盐值重复会破坏安全性，所以每次连接都应使用新盐值。VMess 早期版本依赖时间戳做认证，系统时间偏差过大会直接失败，现在主流实现使用 AEAD 头。VLESS 本身不加密，安全性完全依赖外层 TLS 或 REALITY。Trojan 先完成 TLS，再在隧道内校验密码，外观接近普通 HTTPS。Hysteria2 以 QUIC 为传输，认证后在流上传输数据。

REALITY 的机制是借用真实站点的证书完成握手，客户端通过配置中的公钥验证服务端身份，服务端无需持有自己的域名证书。它改变的是握手外观与证书来源，握手往返次数与普通 TLS 1.3 相同，首字节时间主要受证书链大小与链路往返影响。

### DNS 解析路径

DNS 是独立于代理隧道的一条路径。它可能走系统解析器、运营商解析器、客户端内置解析器，也可能走加密解析器。路径不同，结果与泄漏风险不同。

```text
应用发起查询
   │
   ├─(A) 系统解析器 127.0.0.53 ──► 上游 UDP 53 ──► 递归解析器 ──► 权威服务器
   │                                                    │
   ├─(B) 客户端 fake-ip 或分流规则 ──► 代理内 DNS ──► DoH 443 ──► 加密解析器
   │                                                    │
   └─(C) 直连查询（未进入隧道）──────► 本地运营商解析器 ──► 权威服务器
                                                        │
   判定位：解析器出口 IP 的国家与 ASN 是否等于节点出口？ ◄┘
   不等 → 记录为疑似泄漏或分流；相等 → 记录解析器与 ECS 行为
```

路径 A 的风险是明文查询可被观察与篡改，且解析器位置暴露。路径 B 把查询放进加密连接，但解析器仍然知道查询内容与来源子网。路径 C 在分流规则命中直连时出现，属于设计行为，需要与泄漏区分。

EDNS 客户端子网选项会把客户端的部分地址传给权威服务器，用于 CDN 就近调度。解析结果可能更贴近真实位置，代价是向权威服务器泄露网段信息。记录解析器是否携带该选项，能解释解析到远处节点导致下载慢的现象。

### MTU 与分片

以太网默认最大传输单元 1500 字节，PPPoE 拨号常见 1492 字节，IPv6 要求链路至少支持 1280 字节。TCP 的最大报文段长度由 MTU 减去 IP 头与 TCP 头得出，IPv4 下通常是 1460 字节，IPv6 下通常是 1440 字节。

隧道会额外占用头部空间。WireGuard 在 IPv4 外层下约 60 字节，GRE 约 24 字节，IPsec 依模式不同在几十字节量级。封装后如果不对内层 MSS 做钳制，大包会被分片或丢弃，表现为握手正常、小请求正常、大文件传输卡住。这类故障叫路径 MTU 发现黑洞，排查方法是逐步增大探测包大小，观察从哪个尺寸开始无响应。

检测时记录客户端是否开启 MSS 钳制与分片清理，以及在 1400 字节附近是否出现异常。视频播放与大文件下载对 MTU 问题最敏感。

## 成本模型与预算测算

### 检测不是零成本

检测本身消耗流量、时间与注意力。把这些成本算出来，才能判断一套监测方案是否值得长期运行。下面的公式只做算术，不含任何市场报价。

单次测试的流量消耗：

```text
D_GB = t × B ÷ 8000

D_GB  单方向流量，单位 GB（十进制）
t     测试时长，单位秒
B     平均吞吐，单位 Mbps
```

系数 8000 的来源是把兆比特换算成吉字节：每秒传输 B 兆比特等于 B×10⁶÷8 字节，乘以秒数后除以 10⁹ 得到 GB。

单轮测试的总流量与月度流量：

```text
D_round = (D_down + D_up) × k
D_month = N × R × D_round × D

N  节点数      R  每日轮次      D  观测天数      k  重试系数
```

检测的时间成本：

```text
T_month = N × R × D × t_node ÷ 3600

T_month  小时    t_node  单节点单轮耗时，单位秒
```

订阅的单位流量成本：

```text
C_unit = 月费 ÷ (名义流量 ÷ 倍率)
```

### 测算假设表

下表所有取值都是测算假设，用于演示计算过程，不代表任何真实服务。

| 参数 | 符号 | 取值 | 说明 |
| --- | --- | --- | --- |
| 节点数 | N | 30 个 | 一个订阅内的节点总量 |
| 每日轮次 | R | 3 轮 | 早、晚、夜间各一次 |
| 下行时长 | t_d | 30 秒 | 去掉前 3 秒预热 |
| 下行吞吐 | B_d | 50 Mbps | 示例值，非实测 |
| 上行时长 | t_u | 30 秒 | 反向测试 |
| 上行吞吐 | B_u | 20 Mbps | 示例值，非实测 |
| 观测天数 | D | 30 天 | 一个自然月 |
| 重试系数 | k | 1.2 | 失败重试带来的额外流量 |
| 流量单价 | p | 0.10 元/GB | 测算假设，不是市场报价 |
| 单节点耗时 | t_node | 90 秒 | 准备 20 秒，测试 40 秒，记录 30 秒 |

### 例一：完整吞吐测试的流量

按上表取值，单节点单轮的下行流量为 30×50÷8000，等于 0.1875 GB。上行流量为 30×20÷8000，等于 0.075 GB。两者相加乘以重试系数 1.2，单轮约 0.315 GB。

30 个节点、每日 3 轮、30 天，总轮数为 2700 轮，月度流量约 850.5 GB。按 0.10 元/GB 的测算假设折算，流量成本约 85.05 元。这个数字说明，每天对三十个节点做三轮完整吞吐测试，消耗的流量已经超过多数低价套餐的月额度。

计算过程：

```text
单轮 = (0.1875 + 0.075) × 1.2 = 0.315 GB
月度 = 30 × 3 × 0.315 × 30 = 850.5 GB
成本 = 850.5 × 0.10 = 85.05 元
```

### 例二：轻量可用性监测的流量

把测试换成每 5 分钟一次的握手加一次 HEAD 请求，每次约 20 KB。单节点每日 288 次，消耗约 5.76 MB。30 天约 172.8 MB，即 0.1728 GB。50 个节点的月度流量约 8.64 GB，按同一单价折算约 0.86 元。

```text
单节点日流量 = 288 × 20 KB = 5,760 KB ≈ 5.76 MB
单节点月流量 = 5.76 × 30 = 172.8 MB ≈ 0.1728 GB
50 节点月流量 = 0.1728 × 50 = 8.64 GB
成本 = 8.64 × 0.10 = 0.86 元
```

两种方案差距在两个数量级。可用性监测适合高频运行，吞吐测试适合低频抽样。

### 例三：订阅单位成本

假设月费 15 元，名义流量 200 GB，结算倍率 1.5。实际可用流量为 200÷1.5，约 133.3 GB。单位流量成本为 15÷133.3，约 0.1125 元/GB。

再假设月费 10 元，名义流量 100 GB，倍率 1.0，单位成本 0.10 元/GB。两档价格相差 5 元，单位成本只差 0.0125 元。若每月只用 30 GB，支出分别是 15 元与 10 元，单位成本优势无法兑现。

```text
C_unit = 15 ÷ (200 ÷ 1.5) = 0.1125 元/GB
C_unit = 10 ÷ (100 ÷ 1.0) = 0.10 元/GB
```

### 时间成本常常高于流量成本

按单节点 90 秒计算，30 个节点、每日 3 轮、30 天合计 2,700 次操作，总耗时约 67.5 小时。若按 50 元/小时的测算假设折算，时间成本约 3,375 元，远高于例一的流量成本。

```text
操作次数 = 30 × 3 × 30 = 2,700 次
T_month = 2,700 × 90 ÷ 3600 = 67.5 小时
C_time = 67.5 × 50 = 3,375 元
```

这说明人工逐节点测试只适合一次性验收。长期监测需要脚本化，把准备、执行、记录三段压缩到一次调度里，否则时间成本会压过一切。把 90 秒压到 10 秒，月度耗时降到 7.5 小时，时间成本同步降为 375 元。

### 每次有效结论的成本

```text
C_conclusion = (C_traffic + C_time + C_tool) ÷ V

V  有效结论数，指通过复现检查、可以写入报告的结论条数
```

这个比值比总成本更有决策价值。一次测试产出十个数字，只有两个能通过复现检查，单条结论的成本就是总成本的五倍。提高样本设计的效率，比压低流量单价更能改善这个比值。

## 核验方法与可复现条件 {#method}

这一节是本页的方法基准。其他专题页引用检测口径时，统一指向 [核验方法](/resource-check/#method)，以保证同一套时间、环境、单位与证据规则。

### 四个必要项

时间。记录开始时刻、结束时刻与时区，精确到秒。跨日期比较必须说明是否处于同一时间窗。晚高峰建议单列为 20:00 到 23:00。

环境。记录本地接入方式、签约带宽、实测基线、设备型号、操作系统、客户端与内核版本、代理模式、DNS 配置。缺少任何一项，无法判断是线路表现还是本地条件。

单位。所有数值带单位，方向与统计口径写全。延迟写毫秒并注明是往返还是单向，带宽写 Mbps 并注明单线程或多线程，流量写 GB 或 GiB 并注明换算基准。

证据。保留命令原始输出、状态码、响应头、截图与配置快照。配置快照要脱敏，删除节点地址、认证标识与密码，只保留协议类型、传输方式与规则结构。

### 可复制的命令

下面命令只演示参数与输出字段，不含真实节点地址。执行前替换示例域名，并确认目标服务允许此类请求。

```bash
#1. 通过本地代理取一次 HTTPS 页面，输出各阶段耗时
curl -x http://127.0.0.1:7890 -sS -o /dev/null \
  -w 'code=%{http_code} dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com/

#2. 直接测入口 TCP 握手（需要 tcping 或类似工具）
tcping -c 20 -i 1 example.com 443

#3. 解析路径与解析器出口
dig +short example.com A
dig @1.1.1.1 example.com A +stats
dig +short TXT o-o.myaddr.l.google.com @ns1.google.com

#4. 路径逐跳与丢包
mtr -rwzc 100 example.com

#5. 吞吐，需要自建或被允许的测试服务
iperf3 -c <server> -p 5201 -t 30 -O 3 -P 1
iperf3 -c <server> -p 5201 -t 30 -O 3 -P 8
iperf3 -c <server> -p 5201 -t 30 -O 3 -P 1 -R
```

参数含义要写进记录。`-O 3` 表示丢弃前 3 秒，避开慢启动；`-P 1` 与 `-P 8` 分别是单流与八流；`-R` 表示反向，测的是上行；`-t 30` 是总时长 30 秒；`-c 100` 是发送 100 个探测包。参数不同，结果不可比。

## 安全、隐私与合规边界

### 威胁模型

检测会产生可供观察的痕迹。先列清观察者，再决定记录什么、保留多久。

| 观察者 | 能看到什么 | 风险 | 降低办法 |
| --- | --- | --- | --- |
| 本地网络与运营商 | 目标域名、SNI、DNS 查询、流量时间与体积 | 行为画像、限速、阻断 | 使用加密 DNS，避免明文查询，控制探测频率 |
| 代理运营方 | 连接时间、目标域名、流量体积、可能的明文内容 | 日志留存、二次利用、转售 | 只用测试账号，不登录真实身份，不传敏感文件 |
| 目标服务 | 出口 IP、ASN、账号、浏览器指纹 | 风控标记、账号关联、封禁 | 隔离浏览器配置，测试与日常账号分开 |
| 公开扫描者 | 开放端口、订阅链接、客户端版本 | 节点被滥用、订阅被爬取 | 不公开订阅链接，不暴露管理端口 |
| 本地设备其他程序 | 代理端口、系统代理设置 | 流量被本机程序劫持 | 限制监听地址，检查端口占用 |

检测行为本身也有风险。高频探测会被判定为异常流量，触发验证码或临时封禁。用免费节点对第三方站点做批量扫描，可能违反服务条款与可接受使用政策。检测应控制在低频、少量、目标明确的范围内。

### 不承诺匿名

任何代理工具都不保证匿名。出口 IP 只是链路的一端，浏览器指纹、登录状态、支付信息、时区与语言设置仍然可以关联到人。免费节点的运营方可以看到连接的目标域名与时间，即使内容经过 TLS 加密，元数据仍然暴露访问模式。把敏感账号放在来源不明的节点上，风险高于收益。

### 数据最小化

记录测试结果时，删除节点地址、认证标识、密码与订阅链接。配置快照只保留协议类型、传输方式与规则结构。截图前关闭含个人信息的窗口。

测试账号与日常账号分开。需要登录验证的服务，使用独立邮箱与浏览器配置，测试完成后退出并清理缓存。不要把主账号登录态带进来源不明的节点。

### 合规边界

不同司法辖区对代理服务、内容访问与数据跨境的规则不同。使用前需自行确认当地法律、服务条款与可接受使用政策。本页不提供规避执法或实名制的操作方法。

检测他人运营的节点前，确认条款是否允许压力测试。未授权的吞吐测试可能被视为滥用。公开测试服务通常要求短时、低频使用。

## 分类地图

资源检测专题按八个二级分类组织，每个分类下有两个内容集群，共十六个。分类顺序对应排查顺序，从可用性开始，到数据口径结束。遇到结论冲突时，回到更靠前的分类找原因。

| 分类 | 回答的问题 | 关键判定 | 常见误读 |
| --- | --- | --- | --- |
| 节点可用性 | 这个节点现在能不能用 | 握手、认证、取回三段是否都通过 | 把客户端显示在线当成可用 |
| 延迟、抖动与丢包 | 用起来稳不稳 | P50、P95、抖动与丢包率的组合 | 把单次 ping 当成稳定性 |
| 带宽与吞吐 | 能跑多快 | 单线程与多线程分别达标 | 把多线程峰值当成网页速度 |
| IP 与 DNS | 出口在哪，解析走哪 | 出口归属一致、解析路径可控 | 把国家标签当成解锁能力 |
| 流媒体与 AI 服务 | 目标服务能不能用 | 播放不中断、登录不被拦 | 把一次成功当成长期可用 |
| 监测记录与零结果 | 数据能不能追溯 | 字段完整、证据可复现 | 把没有记录当成没有发生 |
| 测试方法 | 结果能不能比较 | 环境固定、时间窗一致 | 把不同条件下的数字并列 |
| 数据口径 | 数字会不会读错 | 单位、分位、样本量写清 | 把 Mbps 当成 MB/s |

### 八个分类的定位

节点可用性解决“有没有”。它包含 TCP 与 HTTP 探测、端到端验证两个集群，前者判断入口是否可达与状态码是否正常，后者判断完整链路是否成立。可用性判定必须带时间。

延迟、抖动与丢包解决“稳不稳”。它包含 ICMP 与 TCP 延迟、抖动与丢包两个集群。前者解释探测方式的偏差，后者用多次采样描述分布，单次延迟没有稳定性含义。

带宽与吞吐解决“快不快”。单线程测试接近网页与视频的实际体验，多线程测试反映聚合能力与本地瓶颈，两个数字并列才有解释力。

IP 与 DNS 解决“在哪、走哪条路”。出口决定目标服务看到的位置与信誉，DNS 决定解析是否绕过隧道，两条路径要分别验证。

流媒体与 AI 服务解决“目标服务认不认”，判定要区分地区限制、IP 信誉与账号状态。监测记录与零结果解决“能不能追溯”，记录让下一个人复现，零结果避免虚假覆盖。测试方法解决“能不能比较”，数据口径解决“会不会读错”。

## 常见问题

### 为什么 ping 很低，打开网页还是慢？

ping 测的是到节点入口的 ICMP 往返，网页耗时还包含 DNS 解析、代理握手、隧道内建连、TLS 协商、服务器处理与资源加载。入口延迟 30 毫秒而首字节 800 毫秒属于常见组合，差额来自隧道内往返与目标站点。排查顺序是先看首字节时间，再看单线程吞吐，最后看页面资源数量与第三方脚本。把两项指标并列，才能判断慢在链路还是慢在页面。

### 客户端显示 0 毫秒或超时，哪个更可信？

两个都不能直接信。0 毫秒通常意味着测量没有真正发出，可能命中本地缓存、回环地址，或节点尚未启用。超时至少说明那次探测没有得到响应，但原因可能是节点不可达，也可能是探测方式被目标拒绝。可信做法是查看客户端日志里的连接阶段，再用独立命令复测一次，把两次结果与时间一起记录。

### 测速要采多少次才算够？

延迟类指标建议至少 20 次，抖动与丢包建议 100 个包，吞吐测试持续 30 秒并去掉前 3 秒。要报 P95，样本量至少 20 个，因为最近秩法下 20 个样本的第 19 个值就是 P95。样本少于 10 个时分位数没有意义，只能报范围。样本量、采样间隔与时间段都要写进结论，否则读者无法判断稳定性。记录里要写明采样时间与工具版本，工具版本也会影响结果。

### 单线程和多线程差很多，说明什么？

单线程低而多线程高，常见原因是带宽时延积限制了单流窗口。按窗口 256 KiB、往返 180 毫秒计算，单流上限约 11.7 Mbps，增加并发流可以突破。另一个原因是节点对单连接限速。若多线程也上不去，优先怀疑本地接入带宽、探测点 CPU 或加密开销。测试前先测直连基线，基线不达标时，隧道数据没有解释力。两组数据并列，才能定位瓶颈在哪一段。

### 免费节点能不能测出真实带宽？

能测出该时间窗内的真实表现，结论只对这个窗口、这条路径成立。免费节点通常多人共享，带宽随在线人数波动，晚高峰与凌晨可能相差数倍。测量前确认本地基线，测量时记录并发使用情况。把一次结果写成“该节点带宽 100 Mbps”属于过度概括，应写成“某时间窗内单线程吞吐中位数 46.2 Mbps，样本 3 轮”。记录里要同时写明样本数与时间窗。

### 没有自己的服务器，怎么用 iperf3？

可以使用公开测试服务器，但要先看对方的使用规则与频率限制，多数公共节点只允许短时测试。也可以在两台自己控制的设备之间测试，例如本地主机与云服务器，结果更可控。没有服务端时，用大文件单流下载做近似测量，记录文件大小、耗时与来源地址。这种结果与 iperf3 不可直接比较，报告里要注明测量方式。

### DNS 泄漏测试显示泄漏，一定是节点问题吗？

不一定。分流规则把某些域名设为直连、客户端启用 fake-ip、系统同时启用 IPv6，都会让解析路径绕开隧道。判定要看解析器出口地址与查询路径，并区分设计行为与意外泄漏。测试时先关闭分应用代理，固定 DNS 配置，再逐个域名验证。解析器出口与节点出口的国家一致时，仍要检查查询是否走了未加密的 53 端口。

### 出口 IP 显示日本，流媒体还是提示地区限制？

地区只是判定条件之一。目标服务还会看 ASN 类型、IP 历史滥用记录、账号注册地、支付方式与浏览器语言。共享地址池里的地址可能被大量用户使用过，已经进入风控名单。遇到这种情况先记录提示原文与时间，再换一个出口复测，不要直接归因于节点地区不对。同一个出口在登录前后也可能给出不同结果。

### 流媒体检测需要登录账号吗？

分两种情况。只验证首页可访问与地区提示，不需要登录，风险较低。要验证播放与片源库，通常需要登录，此时应使用测试账号，并与主账号隔离。登录态会暴露账号与出口的关联，频繁切换出口可能触发风控。检测记录里要写明是否登录、账号类型、地区设置与测试时间，未登录的结论不能写成可播放。

### AI 服务“能用”的标准是什么？

分四层判定。第一层能打开首页，第二层能完成登录，第三层能提交一次请求并收到完整回复，第四层能连续使用十分钟且不被验证码打断。只通过第一层就写“可用”，结论强度不足。每层记录时间、出口地址与提示原文。验证码拦截要单独标注，它可能来自 IP 信誉，也可能来自行为特征，两者的处理方式不同。

### Mbps 和 MB/s 最容易错在哪？

Mbps 是兆比特每秒，MB/s 是兆字节每秒，两者相差 8 倍，100 Mbps 等于 12.5 MB/s。另一个高频错误是 GB 与 GiB，100 GB 按二进制换算是 93.13 GiB，部分系统把 GiB 显示为 GB，读数会差 7%。第三个错误是把平均值当成分位数，平均 50 毫秒可能掩盖 500 毫秒的尖峰。报告里同时写单位、换算基准与样本量，可以避免大部分误读。换算基准要注明十进制或二进制，三者缺一不可。

### 零结果是不是说明全网没有免费资源？

零结果是本站的收录状态，指当前没有同时满足五项发布标准的条目。它不判断全网是否存在免费资源，也不预测未来是否会出现。读者可以按本页方法自行核验，把时间、环境、单位与证据记录下来。若发现满足标准的公开资源，可以通过纠错渠道提交，核验后再决定是否收录。检测通过只说明某个节点在某个时间窗可用，不构成收录依据。
